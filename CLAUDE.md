## 1. PROJECT OVERVIEW

This is **Riad Sacroud's AI portfolio agent** — a conversational interface that lets recruiters and developers ask natural language questions about Riad and receive accurate, grounded, streamed answers in real time.

**The problem it solves:** A static portfolio site is passive. This app makes Riad's background interactive — instead of a recruiter scanning a PDF, they have a conversation. The agent answers questions like "Is he available?", "What's his main stack?", "Tell me about his projects" — in English or French — without hallucinating, because every answer is grounded in a curated knowledge base via RAG.

**Core user flow:**
1. A recruiter or developer opens the app.
2. They type a question (in English or French).
3. The server embeds the query, retrieves the most relevant knowledge base chunks via vector similarity search, injects them into a system prompt, and streams the response from Claude Haiku.
4. The response appears token-by-token in the chat interface.

## 4. ARCHITECTURE — HOW THE RAG PIPELINE WORKS

### Ingestion flow (run once, or after any KB edit)

```
knowledge-base/*.md
       │
       ▼
scripts/ingest.ts
  1. readKbFiles()        — reads all .md files from /knowledge-base/
  2. chunkText()          — splits each file into 400-word chunks with 50-word overlap
  3. embedChunks()        — sends chunks to Voyage AI (voyage-3, input_type="document")
                            in batches of 64; 200ms delay between batches
  4. clearAndInsert()     — deletes existing rows for each sourceFile,
                            then inserts new chunks one-by-one (fail-fast)
       │
       ▼
kb_chunks table (Neon PostgreSQL + pgvector)
  - content TEXT
  - source_file TEXT
  - chunk_index INTEGER
  - embedding VECTOR(1024)
  - HNSW index on embedding (cosine distance)
```

### Query flow (every user message)

```
User types a question
       │
       ▼
POST /api/chat  (app/api/chat/route.ts)
  1. Parse body: { messages, language? }
  2. detectLanguage(userQuery)          → "fr" | "en"
                                          (heuristic, no external API)
  3. embedQuery(userQuery)              → 1024-dim float array
                                          (Voyage AI, input_type="query")
  4. retrieveRelevantChunks(embedding) → top 4 chunks by cosine similarity
                                          (raw SQL: embedding <=> vector literal)
  5. buildSystemPrompt(chunks, lang)   → system prompt string with:
                                          - language instruction
                                          - resume download instructions
                                          - behavior rules
                                          - chunk context blocks
  6. anthropic.messages.stream(...)    → streaming call to claude-haiku-4-5
                                          max_tokens: 2048
                                          full message history passed
  7. For each content_block_delta:
       encode as: "0:" + JSON.stringify(text) + "\n"
       write to ReadableStream
  8. Emit terminal frame: "d:{\"finishReason\":\"stop\"}\n"
       │
       ▼
Response: text/plain stream with X-Vercel-AI-Data-Stream: v1 header
       │
       ▼
ChatInterface.tsx
  - reads stream line-by-line
  - parses lines starting with "0:" → JSON.parse(line.slice(2))
  - appends text to accumulated string
  - calls setMessages() on every chunk → live rendering
  - sets isStreaming: false when reader signals done
```

### Key detail: asymmetric embedding
Voyage AI is optimized for asymmetric search. During ingestion, `input_type: "document"` is used. During query, `input_type: "query"` is used. This distinction is intentional and meaningful — mixing them up degrades retrieval quality.

## 5. KEY FILES AND WHAT THEY DO

### `lib/db/schema.ts`
Defines all three database tables using Drizzle's `pgTable`. Exports both the table objects (used in queries) and TypeScript types inferred from the schema (`KbChunk`, `NewKbChunk`, etc.). The `kbChunks` table is the only one actively used; the other two are scaffolded for future use. The HNSW index is defined inline using Drizzle's `index(...).using("hnsw", ...)` syntax.

### `lib/db/index.ts`
Creates and exports a single `db` Drizzle instance backed by a Neon HTTP connection. This is the canonical DB client for the application. **Note:** `lib/rag/retrieve.ts` does NOT import from here — it creates its own Neon connection directly. This is an inconsistency that could be cleaned up.

### `lib/rag/embed.ts`
Exports `embedQuery(query: string): Promise<number[]>`. Calls the Voyage AI REST API directly (no SDK) using `fetch`. Uses `input_type: "query"` (important for retrieval quality). Validates that the returned embedding is exactly 1024 dimensions before returning. Throws descriptive errors on API failure.

### `lib/rag/retrieve.ts`
Exports `retrieveRelevantChunks(queryEmbedding: number[]): Promise<RetrievedChunk[]>`. Runs a raw SQL query using the pgvector `<=>` cosine distance operator. Returns `TOP_K = 4` chunks, sorted by ascending distance (most similar first). Converts distance to similarity score (`1 - distance`). Formats the embedding as a pgvector literal string: `[0.1,0.2,...]`. Returns typed `RetrievedChunk` objects.

### `lib/rag/systemPrompt.ts`
Exports `buildSystemPrompt(chunks: RetrievedChunk[], language: "fr" | "en"): string`. Assembles the full system prompt by:
1. Injecting a language enforcement instruction (in French or English).
2. Adding resume/CV download instructions with the correct path based on language.
3. Listing behavior rules (no hallucination, fallback to email, tone guidance).
4. Appending each chunk as a labeled context block showing source file and relevance percentage.

### `lib/detectLanguage.ts`
Exports `detectLanguage(text: string): "fr" | "en"`. Heuristic-based: counts how many words from a hardcoded list of French markers appear in the lowercased input. If more than 1 French marker is found, returns `"fr"`, otherwise `"en"`. No external API call. Falls back to English on ambiguity. Strips non-letter characters (including accented letters) before checking.

### `app/api/chat/route.ts`
The only API route. Handles `POST /api/chat`. Runs the full RAG pipeline synchronously (embed → retrieve → build prompt), then streams Claude's response as a `ReadableStream`. The stream format is a hand-rolled version of the Vercel AI SDK data stream protocol: each text delta is emitted as `0:"text"\n`; the terminal frame is `d:{"finishReason":"stop"}\n`. Sets `runtime = "nodejs"` and `maxDuration = 30` (Vercel limits). Accepts a full message history from the client to support multi-turn conversations. Accepts an optional `language` field from the client; if absent or invalid, falls back to `detectLanguage`.

### `scripts/ingest.ts`
Standalone Node.js script (run via `npx tsx`). Not part of the Next.js app — runs offline. Reads `.env.local` explicitly via `dotenv`. Four-phase pipeline: read → chunk → embed → clear+insert. Clears rows by `sourceFile` (not the entire table), so you can re-ingest one file without touching others if you modify `clearAndInsert` to target a single file. Currently clears all files found in the current run. Inserts one row at a time (slow but fail-safe — identifies exactly which chunk fails). Validates embedding dimensions and NaN values before each insert.

### `app/components/ChatInterface.tsx`
Root client component (`"use client"`). Manages all application state: `messages`, `input`, `isLoading`, `isMobile`. Detects mobile breakpoint at 768px via a resize listener. Renders `<LeftPanel>` only on non-mobile. On mobile, shows a compact header and inline suggested questions. The `sendMessage` callback builds the message history (excluding the placeholder assistant message), POSTs to `/api/chat`, then reads the response stream line-by-line, parsing `0:` lines and calling `setMessages` on every chunk to produce live streaming UI. Uses `AbortController` to cancel in-flight requests. Auto-resizes the textarea up to 120px. Enter submits; Shift+Enter inserts a newline.

### `app/components/LeftPanel.tsx`
Client component. Static sidebar shown only on desktop. Displays avatar (`/riad-photo.png`), name, title, an animated availability badge, a language note, 6 suggested question chips (mix of English and French), and social links (GitHub, LinkedIn, email). Suggested questions call `onSuggestedQuestion` prop which maps to `sendMessage` in the parent. Hover states are managed with local `useState<number | null>`.

### `app/components/MessageBubble.tsx`
Client component. Exports the `Message` interface (used as a type in `ChatInterface.tsx`). User messages are right-aligned in a simple bubble. Assistant messages are left-aligned with a small accent dot, rendered through a custom `MarkdownRenderer`. The renderer handles: H1, H2, H3, horizontal rules, bullet lists, numbered lists, empty lines, and plain paragraphs. Inline rendering (`renderInline`) handles: `**bold**`, `*italic*`, `` `code` ``, full `https://` URLs, email addresses, plain domain patterns (auto-prefixed with `https://`), and relative `.pdf` paths (rendered as styled download buttons). A blinking cursor `▊` is shown while `isStreaming` is true.

## 6. DATABASE SCHEMA

### `kb_chunks` — Active, populated by ingestion

| Column | Type | Constraints | Purpose |
|---|---|---|---|
| `id` | `uuid` | PK, `gen_random_uuid()` | Unique row identifier |
| `content` | `text` | NOT NULL | Raw text of the chunk (what the LLM reads) |
| `source_file` | `text` | NOT NULL | Name of the source `.md` file without extension (e.g. `"skills"`) |
| `chunk_index` | `integer` | NOT NULL | 0-indexed position within the source file |
| `embedding` | `vector(1024)` | NOT NULL | 1024-dimensional float vector (Voyage AI `voyage-3`) |
| `created_at` | `timestamp` | NOT NULL, `now()` | Ingestion timestamp |

**Index:** `kb_chunks_embedding_idx` — HNSW index on `embedding` using `vector_cosine_ops`. This enables fast approximate nearest-neighbor search. The `<=>` operator (cosine distance) uses this index automatically.

**Vector dimensions:** 1024 — produced by Voyage AI `voyage-3` model. `voyage-3-lite` produces 512 dimensions and is incompatible with this schema. Do not change the model without dropping and recreating the table.

## 10. FRONTEND ARCHITECTURE

### Component hierarchy

```
app/page.tsx
  └── <ChatInterface>           (client, manages all state)
        ├── <LeftPanel>         (client, desktop only)
        └── <MessageBubble>     (client, one per message)
              └── <MarkdownRenderer>   (inline, no separate file)
                    └── renderInline() (inline function)
```

### How `ChatInterface.tsx` orchestrates everything

- Holds `messages: Message[]` — the source of truth for the conversation.
- Holds `isLoading` to prevent concurrent sends.
- Holds `isMobile` (boolean) determined by `window.innerWidth < 768` on mount and resize.
- `sendMessage(content)` is the central action: it optimistically adds both the user message and an empty assistant placeholder to state, then starts the streaming fetch.
- An `AbortController` ref lets the user's browser cancel an in-flight request (though no cancel UI is exposed currently).
- The textarea auto-grows up to 120px via a `useEffect` that reads `scrollHeight` after every `input` state change.

### How streaming is handled

The server streams `text/plain` with each token as a line: `0:"token text"\n`. The client reads the `ReadableStream` body via `response.body.getReader()`, decodes chunks with `TextDecoder({ stream: true })`, splits on newlines, and for each line starting with `"0:"` parses the JSON string after the prefix. The accumulated text is written back to the assistant message in state on every chunk — producing live token-by-token rendering.

The terminal frame `d:{"finishReason":"stop"}\n` is sent by the server but currently ignored by the client (the `done` flag from the reader signals completion instead).

### How `MessageBubble.tsx` renders markdown

`MarkdownRenderer` is a line-by-line state machine — not a library. It iterates lines and matches:
- `# ` → H1 (display font, 1.1rem)
- `## ` → H2 (mono font, uppercase, accent color)
- `### ` → H3 (mono font, uppercase, muted)
- `---` → horizontal rule
- `- ` or `* ` → bullet with `▸` marker in accent color
- `\d+. ` → numbered list with accent-colored number
- empty line → 0.5rem spacer div
- anything else → plain paragraph

`renderInline` then handles inline tokens within each line: `**bold**`, `*italic*`, `` `code` ``, `https://` URLs, email addresses (`x@y.z`), plain domain patterns (auto-linked with `https://`), and `/x.pdf` paths (rendered as styled download buttons with language-aware labels).

### How `LeftPanel.tsx` works

Desktop-only sidebar (hidden below 768px via `isMobile` check in `ChatInterface`). Contains:
- Avatar: `<img src="/riad-photo.png">` in a 72×72 circle
- Name (`Riad Sacroud`), title (`Full-Stack Engineer`)
- Animated availability badge (pulsing green dot + "Available · CDI & Freelance")
- Language note: "Ask in English or French — the agent detects your language automatically."
- 6 suggested question chips (clicking calls `onSuggestedQuestion` → `sendMessage` in parent)
- Social links: GitHub (`sacroudr`), LinkedIn, email

### Language detection

Language is detected **per message**, **server-side**, in `lib/detectLanguage.ts`. There is no global language toggle. The client does not send a language preference (the `language` field in the request body is always absent from `ChatInterface.tsx`). The server detects from the latest user message content and instructs Claude to respond in that language. This means within a single conversation, the language can switch per turn if the user switches languages.

## 11. IMPORTANT DECISIONS AND CONSTRAINTS

**Why RAG instead of a large system prompt?**
A static system prompt stuffed with all KB content would hit token limits and be expensive. RAG retrieves only the 4 most relevant chunks per query, keeping context lean and focused. It also scales: adding more KB files doesn't increase per-request cost.

**Why `voyage-3` over `voyage-3-lite`?**
`voyage-3` produces 1024-dimensional embeddings; `voyage-3-lite` produces 512. Richer embeddings capture more semantic nuance, which improves retrieval accuracy for a small KB where false positives matter. Cost difference is negligible at this scale.

**Why Claude Haiku 4.5 over Sonnet or Opus?**
This is a retrieval-augmented Q&A system, not a reasoning-heavy task. The context is injected — the model mainly needs to synthesize and present it. Haiku is significantly cheaper and faster to stream. For this use case (portfolio agent answering pre-grounded questions), quality difference vs Sonnet is negligible.

**Why Neon + pgvector instead of Pinecone?**
This project already needs a relational database (for `chat_sessions` / `chat_messages`). Consolidating on one DB (Neon + pgvector) avoids a second service, second API key, and synchronization complexity. Neon's serverless model matches Vercel's serverless deployment. At this scale (a few hundred KB chunks), pgvector with an HNSW index is more than sufficient.

**Why inline styles instead of Tailwind in components?**
The design system is entirely CSS custom property-based (variables like `--accent`, `--font-mono`, `--radius`). Inline styles that reference these variables keep the design tokens centralized in `globals.css` without needing Tailwind class mappings. This also avoids Tailwind's JIT purging risks and makes computed/dynamic styles (like hover states via `onMouseEnter`) straightforward.

**Why is language detection per-message and server-side?**
Simplicity and accuracy. A global toggle would require UI state and client-side session management. Per-message detection requires no UI and handles multilingual conversations naturally. Server-side detection keeps the logic in one place and means the client doesn't need to know anything about language.

**Why are `chat_sessions` and `chat_messages` scaffolded but not implemented?**
They represent the next phase of the product: conversation logging for analytics and admin review. The schema and migration are already applied to the database so the tables exist. No code writes to them yet — this avoids unnecessary DB writes until the feature is ready to be designed properly.

## 12. WHAT NOT TO TOUCH

**`lib/rag/embed.ts`** — Any change to the embedding model, dimensions, or `input_type` here must be matched in `scripts/ingest.ts`. Mismatches will silently corrupt retrieval (queries and documents will be in different vector spaces). If you change the model, you must also update the schema dimensions and re-run ingestion from scratch.

**`lib/rag/retrieve.ts`** — The `TOP_K = 4` value and the cosine distance operator (`<=>`) are tuned for the current KB size and embedding model. Changing `TOP_K` affects context window usage and response quality. The raw SQL format of the vector literal (`[x,y,...]`) is required by pgvector — do not try to pass it as a JS array.

**`lib/rag/systemPrompt.ts`** — The behavior rules and language instruction directly control what the agent says. Changing this changes the agent's persona and guardrails. The resume link logic (`/resume-fr.pdf`, `/resume-en.pdf`) must remain consistent with what's actually in `/public/`.

**`scripts/ingest.ts`** — Wrong chunking parameters (especially `CHUNK_SIZE` and `CHUNK_OVERLAP`) will produce chunks that are semantically incoherent or too granular. Any change here requires a full re-ingestion. The per-row insert strategy is intentional for debuggability — don't replace it with a bulk insert without adding equivalent error isolation.

**`knowledge-base/*.md`** — These files are the source of truth for everything the agent says. Edits require `npm run ingest` to take effect. Content errors here propagate directly into agent responses.

**`lib/db/schema.ts`** — Schema changes require `npx drizzle-kit push` (or a new migration) and may require data migration for existing rows. The `vector(1024)` dimension is a hard constraint tied to the embedding model. Do not change it without replacing all existing vectors.
